My LFX Linux Kernel Bug Fixing Mentorship with Shuah Khan has ended, and my main write-up stays as it is. This post is the log of every patch I get merged from here on: a short entry for each one, and a row in the results table.

Results

vmxnet3: a DMA mapping of memory that can’t be mapped

net-next, applied by Jakub Kicinski on 12 November 2026. Reviewed by Simon Horman.

Bug. syzbot reported rejecting DMA map of vmalloc memory from vmxnet3, the driver for VMware’s paravirtual NIC. Probe maps the whole struct vmxnet3_adapter with dma_map_single(), but the adapter lives in the net_device private area, which kvzalloc() falls back to vmalloc() for under memory pressure. Then the mapping fails, probe fails, and the VM has no network.

Fix. The mapped address is only handed to the device as optional “driver data”, which the per-queue descriptors in the same driver already leave empty, and which DPDK’s vmxnet3 driver never sets. So the patch drops the mapping and reports no driver data (3 lines added, 17 removed):

-   devRead->misc.ddPA = cpu_to_le64(adapter->adapter_pa);
-   devRead->misc.ddLen = cpu_to_le32(sizeof(struct vmxnet3_adapter));
+   devRead->misc.ddPA = cpu_to_le64(~0ULL);
+   devRead->misc.ddLen = cpu_to_le32(0);

Tested in QEMU (-device vmxnet3) with syzbot’s reproducer and with fail_page_alloc forcing large allocations to fail on rebind: before, the NIC disappeared; after, it binds and pings.

Review. Jakub deferred v1: “this does not seem like a real fix. If nobody complained about this failure mode for 13 years chances are we break more than we fix here.” He asked for net-next instead of net, no Fixes: tag, and no argument about the mapping never being synced, which doesn’t apply to a virtual device. v2 had the same code, went out the day after net-next reopened, and was applied two days later.

Lesson. A fuzzer report isn’t automatically a stable fix, and one weak argument in a commit message is the one the reviewer replies to.

xilinx-ams: more channels than the buffer has room for

iio togreg, applied by Jonathan Cameron on 14 November 2026. Reviewed by Sai Krishna Potthuri, binding acked by Krzysztof Kozlowski.

Bug. ams_parse_firmware() allocates room for 51 channel specs and fills them from the device tree without tracking how much room is left. The PL node always adds its 10 fixed channels, numbered 20 to 29, and then one more for each channel@N child. Any N from 20 to 50 was accepted, so a child numbered 20 to 29 duplicated a fixed channel and the PL node could reach 41 channels with only 31 budgeted, writing past the end of the buffer. A reg below 20 also made the unsigned index wrap, reading far outside ams_pl_channels[].

Fix. Accept only the external channels 30 to 50, in both the driver and the binding, and pass the remaining capacity down so a module that doesn’t fit fails with -ENOSPC:

    if (reg < AMS_PL_EXT_CHANNEL_MIN ||
        reg > AMS_PL_EXT_CHANNEL_MAX)
        continue;

    if (num_channels >= max_channels)
        return -ENOSPC;

Compile-tested only, as I don’t have ZynqMP hardware. dt_binding_check passes and rejects a channel@25 node.

Review. Sai pointed out that channels 20 to 29 are the fixed ones, so the binding itself was too permissive. v3 became a two-patch series, with the binding limited to 30-50 first.

Lesson. The bounds check stops the overflow, but the hardware’s owner knew why the bad input existed at all.

sx9310 and sx9360: gains that wrapped around

iio togreg, applied by Jonathan Cameron on 14 November 2026. Reviewed by Andy Shevchenko.

Bug. Both write_gain() functions put ilog2(val) into a small register field without checking it, and still reported success. On sx9310, a gain of 16 wrapped around to 1. On both drivers, 0 and negative values selected the highest code in the field, because ilog2(0) is -1.

Fix. Return -ERANGE for values that can’t be represented. For sx9310 that is whatever doesn’t fit the 2-bit field:

    if (val <= 0)
        return -ERANGE;

    gain = ilog2(val);
    ...
    if (!FIELD_FIT(SX9310_REG_PROX_CTRL3_GAIN0_MASK, gain))
        return -ERANGE;

FIELD_FIT() isn’t enough for sx9360, whose 3-bit field also holds codes 4 to 7 that the driver doesn’t support, so it compares against the code for a gain of 8. Compile-tested only.

Review. v1 rejected every unsupported value. Jonathan asked me to keep rounding values between the supported gains down, so the ABI doesn’t change, and Andy asked for -ERANGE instead of -EINVAL. On v3, Andy wrote: “Now it looks better.”

Lesson. Rejecting bad input can still break userspace, so reject only what was never meaningful.

sx9324: a range check that could never fire

iio togreg, applied by Jonathan Cameron on 15 November 2026. Reviewed by Joshua Crofts.

Bug. sx9324_read_gain() is meant to return -EINVAL for the reserved gain codes 0 and 5 to 7, but the check sat in the else of if (regval), where regval is always 0. Codes 5 to 7 were reported as gains of 16, 32 and 64, which the sensor doesn’t support and write_raw() rejects.

Fix. Check both reserved ranges before converting the code to a gain (3 lines added, 5 removed):

-   if (regval)
-       regval--;
-   else if (regval == SX9324_REG_PROX_CTRL0_GAIN_RSVD ||
-        regval > SX9324_REG_PROX_CTRL0_GAIN_8)
+   if (regval == SX9324_REG_PROX_CTRL0_GAIN_RSVD ||
+       regval > SX9324_REG_PROX_CTRL0_GAIN_8)
        return -EINVAL;

-   *val = 1 << regval;
+   *val = 1 << (regval - 1);

Compile-tested only, as I don’t have SX9324 hardware.

Lesson. A condition in an else branch inherits the opposite of the if, so read it with that in mind.

sx9310: “off” selected the strongest filter

iio togreg, applied by Jonathan Cameron on 15 November 2026.

Bug. The binding allows semtech,proxraw-strength values of 0, 2, 4 and 8, where 0 turns the filter off. The driver converts the property with ilog2(), which returns -1 for 0, and FIELD_PREP() masks that to 3 in the 2-bit field. A board asking for no filter got the same setting as <8>, the strongest one.

Fix. Keep 0 as register code 0:

-       } else {
+       } else if (raw) {
+           /* 0 means off; 2, 4 and 8 are codes 1 to 3. */
            raw = ilog2(raw);
        }

No in-tree device tree uses <0>, so this only affects out-of-tree boards. I checked the mapping with a userspace copy of the conversion: before the patch 0 and 8 both give code 3, and after it 0 gives 0.

Lesson. ilog2(0) was behind the gain bugs above too, so once a bad pattern turns up in a driver family it’s worth searching for the rest.

ALSA: my laptop was matched as a Legion

sound for-linus, applied by Takashi Iwai on 17 November 2026.

Bug. On my Lenovo V14 G2 ITL, dmesg said ALC257: picked fixup for codec SSID 17aa:38b7. The controller’s PCI subsystem ID (17aa:380e) matches nothing in the quirk table, so the driver falls back to the codec’s ID (17aa:38b7) and finds the entry for a Legion Slim 7 whose PCI ID is 17aa:38b7. That sets up two CS35L41 amplifiers this laptop doesn’t have.

Fix. A codec-ID-only entry, placed right after the Legion’s:

    SND_PCI_QUIRK(0x17aa, 0x38b7, "Legion Slim 7 16APH8", ALC287_FIXUP_CS35L41_I2C_2),
    /* Lenovo V14 G2 ITL has PCI SSID 17aa:380e and codec SSID 17aa:38b7, which
     * falls back to the Legion Slim 7 16APH8 entry above; this must come after it
     */
    HDA_CODEC_QUIRK(0x17aa, 0x38b7, "Lenovo V14 G2 ITL", ALC269_FIXUP_LENOVO_XPAD_ACPI),

The lookup stops at the first match, so the order matters: placed after it, a real Legion still matches on its PCI ID first. The fixup is the one the generic Lenovo fallback would have given this machine. I tested it on the laptop by forcing the same fixup (lenovo-xpad-led) from the command line: speakers, headphones and both microphones worked as before.

Review. “Applied now. Thanks.”, the same day, with no changes.

Lesson. My own dmesg is a good place to look for bugs, and having the hardware made the patch easy to test and to accept.

ideapad-laptop: power profiles for my laptop

platform-drivers-x86 review-ilpo-next, applied by Ilpo Järvinen on 19 November 2026. Reviewed by Rong Zhang.

Bug. My V14 G2 ITL controls its power profiles with DYTC version 4, which ideapad-laptop only trusts on models listed in an allow table. Every boot logged DYTC_VERSION 4 support may not work, and no platform_profile was registered, so desktop power-profile switches did nothing.

Fix. Add the laptop to ideapad_dytc_v4_allow_table[]:

    {
        /* V14 G2 ITL */
        .matches = {
            DMI_MATCH(DMI_SYS_VENDOR, "LENOVO"),
            DMI_MATCH(DMI_PRODUCT_VERSION, "V14 G2 ITL")
        }
    },

I tested it on the laptop with ideapad_laptop.allow_v4_dytc=Y, which takes the same code path. All three profiles register and read back, and the firmware applies them: with all CPUs busy on AC power, the package drew about 14 W in low-power, 17 W in balanced and 24 W in performance.

Review. Rong gave a Reviewed-by and asked whether Fn+Q switches profiles under Windows, since then the Linux side could be improved too.

Lesson. A warning that appears on every boot is a bug report waiting to be written, and measured numbers make a one-line table entry easy to accept.
