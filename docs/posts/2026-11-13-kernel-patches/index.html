My LFX Linux Kernel Bug Fixing Mentorship with Shuah Khan has ended. My main write-up and my final report are with Shuah, so I am leaving that post as it is, at fifteen applied patches. I am still sending patches, though, and some of them were already on the mailing list when the mentorship ended. This post picks up from there. Each time a patch is applied, I will add a section about it, a row in the results table and a bar in the timeline.

The first one is in a network driver rather than IIO. It also taught me something that none of my IIO patches did: a correct fix can still be the wrong kind of fix for the tree you send it to.

First published on 13 November 2026 with the vmxnet3 fix. Updated on 17 November 2026 with an ALSA fix for my own laptop.

vmxnet3: a DMA mapping of memory that can’t be mapped

vmxnet3 is the driver for VMware’s paravirtual network card, the one most Linux virtual machines on ESXi use. syzbot, Google’s kernel fuzzer, reported a warning from it while it was running with page allocation fault injection:

rejecting DMA map of vmalloc memory

The cause is in vmxnet3_probe_device(). The driver keeps its state in struct vmxnet3_adapter, which is the private area of the net_device. alloc_netdev_mqs() allocates that area with kvzalloc(). That function first tries for physically contiguous memory, and if that fails it falls back to vmalloc(). The adapter embeds 32 transmit and 32 receive queues, so it is well over a page, and a large contiguous allocation is exactly the kind that fails under memory pressure, or under fault injection.

The driver then mapped the whole adapter for DMA:

    adapter->adapter_pa = dma_map_single(&adapter->pdev->dev, adapter,
                         sizeof(struct vmxnet3_adapter),
                         DMA_TO_DEVICE);
    if (dma_mapping_error(&adapter->pdev->dev, adapter->adapter_pa)) {
        dev_err(&pdev->dev, "Failed to map dma\n");
        err = -EFAULT;
        goto err_set_mask;
    }

dma_map_single() only works on memory that is physically contiguous, so when the adapter is in vmalloc memory it warns and returns an error. Probe then fails, and the VM has no network card.

What was the mapping for?

Before deleting anything, I needed to know what the device did with this address. It goes into the area the driver shares with the virtual device, as the “driver data”:

    devRead->misc.ddPA = cpu_to_le64(adapter->adapter_pa);
    devRead->misc.ddLen = cpu_to_le32(sizeof(struct vmxnet3_adapter));

Three things suggested the device doesn’t need it:

  • The same driver already opts out elsewhere. Every per-queue descriptor in vmxnet3 reports “no driver data” with ddPA = ~0ULL and ddLen = 0.
  • Other drivers for the same device never set it. The vmxnet3 driver in DPDK leaves misc.ddPA alone entirely.
  • The device couldn’t use it anyway. The adapter is full of kernel pointers and locks. A hypervisor has no meaningful way to interpret a copy of it.

So the fix removes the mapping and reports no driver data in the shared area, in the same way the queues already do:

-   devRead->misc.ddPA = cpu_to_le64(adapter->adapter_pa);
-   devRead->misc.ddLen = cpu_to_le32(sizeof(struct vmxnet3_adapter));
+   devRead->misc.ddPA = cpu_to_le64(~0ULL);
+   devRead->misc.ddLen = cpu_to_le32(0);

The rest of the patch is deletion: the dma_map_single() call, its error path, the two dma_unmap_single() calls in the probe error path and in remove, and the adapter_pa field. In total it is 3 lines added and 17 removed, and probe loses a way to fail.

Testing it without VMware

I don’t have an ESXi host, but QEMU emulates a vmxnet3 card (-device vmxnet3), and the kernel has fail_page_alloc to make page allocations fail on demand. I built a kernel with KASAN and CONFIG_DMA_API_DEBUG, and tested three things before and after the patch:

The third row is the one that matters. It is the real-world version of syzbot’s report: a VM under memory pressure that reloads the driver and loses its network. I listed all of this under the --- line and added “Not tested on ESXi”.

Review: “this does not seem like a real fix”

Simon Horman reviewed v1 four days later and gave it a Reviewed-by: with no changes. A few hours later Jakub Kicinski, one of the networking maintainers, replied:

Sounds fair but this does not seem like a real fix. If nobody complained about this failure mode for 13 years chances are we break more than we fix here.

Please repost this for net-next in a couple of weeks without a Fixes tag.

Also please remove the “never synced” stuff. That’s purely relevant for intentionally hamstrung kernels. This is virt, there’s no DMA to sync other than swiotlb.

followed by pw-bot: defer, which tells the netdev patchwork bot to set the patch aside.

Neither point was about whether the code was right. They were about where it belonged.

net versus net-next. I had sent v1 to net, the tree for fixes that go to Linus during the current release cycle and then to stable kernels, and I had added a Fixes: tag pointing at the 2013 commit that introduced the mapping. Jakub’s point was that this is not how a maintainer measures a bug. The failure needs fault injection or serious memory pressure, nobody had reported it in thirteen years, and the patch changes what the driver tells a hypervisor I could not test against. Backporting that to every stable kernel risks more than it fixes. As a cleanup in net-next, it gets a full release cycle of testing first. When he deferred it, net-next was closed for the merge window, so “a couple of weeks” meant waiting for it to reopen.

“Never synced”. My commit message argued that the driver data was useless because the mapping was DMA_TO_DEVICE, made once and never synced, so the device could only ever see a stale copy. That sounded convincing to me, but Jakub pointed out that it doesn’t apply here. A virtual device reads guest memory directly, so syncing only matters with a bounce buffer such as swiotlb. The argument would have been true for real hardware, but it was wrong for this driver. The other reasons, the per-queue descriptors and DPDK, were enough on their own, so v2 drops that sentence.

v2 had the same code. It targets net-next, has no Fixes: tag, drops the sync argument and carries Simon’s Reviewed-by:. I sent it the day after net-next reopened, and Jakub applied it two days later.

ALSA: my laptop was matched as a Legion

The second patch came from my own laptop, a Lenovo V14 G2 ITL. While I was looking at why its speakers sound thin, I noticed this line in dmesg:

ALC257: picked fixup  for codec SSID 17aa:38b7

A “fixup” in the HD-audio driver is a machine-specific tweak: pin configurations, amplifier setup, LED handling and so on. The driver picks one by looking up the machine’s IDs in a long table of quirks. There are two IDs to look at: the PCI subsystem ID of the audio controller, and the subsystem ID the audio codec itself reports. On most machines they are the same. On mine they are not:

How the lookup goes wrong

snd_hda_pick_fixup() tries the PCI ID first. Nothing in the table matches 17aa:380e, so it falls back to the codec ID, 17aa:38b7, and finds this entry:

    SND_PCI_QUIRK(0x17aa, 0x38b7, "Legion Slim 7 16APH8", ALC287_FIXUP_CS35L41_I2C_2),

That entry was written for a Lenovo Legion Slim 7 whose PCI ID is 17aa:38b7. The codec-ID fallback doesn’t know that, so my laptop got the Legion’s fixup, which sets up two Cirrus Logic CS35L41 smart amplifiers. The V14 G2 ITL has no CS35L41 at all. Its speakers are driven directly by the ALC257 codec, through a single pin.

The fix, and why its position matters

The table has a macro for exactly this case, HDA_CODEC_QUIRK(), an entry that only matches on the codec ID. The patch adds one:

    SND_PCI_QUIRK(0x17aa, 0x38b7, "Legion Slim 7 16APH8", ALC287_FIXUP_CS35L41_I2C_2),
    /* Lenovo V14 G2 ITL has PCI SSID 17aa:380e and codec SSID 17aa:38b7, which
     * falls back to the Legion Slim 7 16APH8 entry above; this must come after it
     */
    HDA_CODEC_QUIRK(0x17aa, 0x38b7, "Lenovo V14 G2 ITL", ALC269_FIXUP_LENOVO_XPAD_ACPI),

The interesting part is where it goes. The lookup walks the table once, in order, and stops at the first match. Codec-only entries are checked against the codec ID during that same walk. If my entry came before the Legion’s, a real Legion Slim 7, whose codec probably reports 17aa:38b7 too, would match my entry first and lose its amplifier setup. Placed after it, the Legion still matches on its PCI ID first, and my laptop, whose PCI ID matches nothing, carries on down the table to the new entry. The comment is there so the next person who sorts that table doesn’t move it.

For the fixup itself I picked ALC269_FIXUP_LENOVO_XPAD_ACPI, because that is what the driver’s generic Lenovo fallback would give this machine if the Legion entry weren’t in the way. In other words, the patch gives the V14 G2 ITL the fixup it would have had all along.

Testing on the real machine

This time I had the hardware, so I could test the result rather than only build it. The driver lets you force a fixup by name from the kernel command line, and lenovo-xpad-led is the model name for the same fixup. After booting with it, dmesg said picked fixup lenovo-xpad-led (model specified), and the speakers, headphones, headset microphone and internal microphone all worked as before.

The thin speaker sound I started out with turned out to be a separate problem. The codec has a single speaker output, and Windows makes it sound better with signal processing that Linux doesn’t do. That is a job for an equaliser in PipeWire, not a kernel patch.

Review: “Applied now. Thanks.”

I sent the patch to Takashi Iwai, the sound maintainer, at 01:25 IST, and he applied it the same afternoon, with no changes, to the for-linus branch of the sound tree. That branch carries fixes to Linus during the current release cycle, so this one should reach a release candidate soon rather than waiting for the next merge window.

What these reviews taught me

  • A bug report is not automatically a fix for stable. Whether something goes to net or net-next depends on who is actually hurt and how risky the change is, not on whether a fuzzer found it. Before adding a Fixes: tag, I now ask whether a stable maintainer would want this backported to a kernel running in production.
  • Every argument in a commit message has to hold. One weak reason in a list of good ones is what the reviewer will reply to. If a reason only holds on real hardware, it doesn’t belong in a commit message for a paravirtual driver.
  • Deferred is not rejected. pw-bot: defer with “repost in a couple of weeks” is an instruction, not a no. I resent the patch the day after the tree reopened.
  • Your own machine is a good place to look for bugs. The ALSA bug was in my dmesg the whole time. Having the hardware also meant I could test the change properly, which made the patch much easier to accept.
  • In a first-match table, order is part of the fix. The new entry is only correct because of where it sits, so I put that in a comment, not just in the commit message.
